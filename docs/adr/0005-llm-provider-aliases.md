# Reuse bundled provider names for IV aliases

One IV endpoint serves several surfaces, each distinguished by auth token, and `llm/*.yaml` names them inconsistently: the Codex surface is `openai` under `pi`, `omp`, `opencode`, and `craft-agents` but `iv-codex` under `codex` and `hermes`, and the same split applies to `anthropic` versus `iv-cc`. Read as a naming slip this invites unification on the explicit `iv-*` form, which is also the more honest name — nothing about `openai` says the requests go to `llm.invalley.co`. That rename is silently lossy. The alias becomes the provider key in the generated `models.json` / `models.yml`, and the consuming tool uses that key to look up its own bundled catalog: pi's `applyModelsJson` starts from the built-in provider's model list and upserts our declared entries by id, so ids the tool already ships keep their real costs, context windows, and limits. An alias the tool does not recognize starts from an empty list and gets only what we enumerate. The tools using `iv-*` are the ones with no catalog to inherit.

Alias names therefore follow the consuming tool, not the endpoint: reuse the bundled provider's name where the tool has one, and use an explicit `iv-*` name where it does not. The cost is that a provider name no longer identifies an endpoint on its own, so `llm/model-endpoint` and the surrounding comments carry that mapping. The consequence that must be respected everywhere: because our entries are merged into a bundled catalog rather than replacing it, a model id can exist on several providers at once, and a bare id is resolved against that union. Pin the provider on any id that more than one alias can serve. A bare `gpt-5.6-sol` in `pi.yaml` resolved against pi's bundled openrouter catalog instead of IV — same id, wrong endpoint, no error. Bare ids and globs stay correct where the match is unambiguous or where breadth is the point: `claude-opus-5*` is meant to surface both the `anthropic` and `iv` copies, and an alias that resolves to nothing warns at startup.
